# The Future of Data Platform in 2026

작성일: 2026-10-13

## 동기

작년인가 올해 초 쯤에 `Airbridge Data System 2.0`이란 주제로 사내 발표를 했었다. 데이터 웨어하우스를 담당하면서 어떻게 더 고도화 해야할지, 나아갈 길이 무엇인지 제시했다. 당시 내세웠던 데이터 플랫폼의 3가지 단계는 **1. Data Ready, 2. Analytics Ready, 3. AI Ready**였다.(지금 생각해도 거시적으로는 올바른 방향인 것 같다.) 1년 정도 지났으니 정리하는 겸, 어떤 것들이 더 추가되면 좋을지 트렌드를 살펴보고 어떤 커리어를 쌓아나가면 좋을지 작성해보려한다.

요약하자면 **Physical - Logical - Business - Semantic - Insight**를 만들기 위한 플랫폼을 단계적으로 개발하는 방법에 이야기해보려 한다.

## 데이터 플랫폼의 미래

그 당시 발표 내용과 지금 드는 생각을 같이 정리한다.

### 1. Data Ready

데이터 플랫폼의 기초는 올바른 데이터를 제공하는 것이다. 올바른 데이터를 제공하려면 어떤 원칙이 필요한지 기술한다.

- `Reliable`: **신뢰할 수 있는 데이터를 제공**해야한다. 데이터 일관성, 품질 등의 용어가 있지만 내가 생각하는 신뢰는 **Data as expected**이며 반대로 **Unexpected == 데이터 장애**라고 생각한다.
- `Auditable`: 접근통제, 권한설계, 감사로그를 통해 **데이터에 대한 행동이 감사, 추적 가능**해야한다. 데이터에 관련한 문제를 해결하기 위한 최소한의 방법을 두는 것을 의미한다.
- `Sustainable`: 데이터 관련 행동이 식별, 추적 가능하며 비즈니스 지속 가능성을 고려하여 **비용-합리적**이어야 한다.

하나가 기억나지 않는데, 지금 생각해보면 Scalable? Timeliness? 일 거 같다. (아마도 Timeliness)

- `Scalable`: 요구사항들로 인해 관리 포인트가 많아지더라도 확장 가능한 형태여야한다. terraform, dbt를 통한 IaC를 예로 들 수 있다.
- `Timeliness`: 사용자가 요구한 시간에 제공되어야한다. 데이터 파이프라이닝, 파티션/인덱스 설계, 쿼리 및 서빙이 잘 구성되어야한다.
 
### 2. Analytics Ready

데이터가 준비됐다면 사용자가 원하는 데이터를 쉽게 얻을 수 있어야한다. 그렇다면 어떻게 "찾고", "계산"할지 기술한다.

- `Discoverable`: 사용자가 **필요한 데이터를 쉽게 찾을 수 있어야** 한다. DataHub 혹은 Databricks의 Unity Catalog를 통해 찾고자 하는 정보가 검색 가능해야한다. Searchable을 쓸 수 있었지만 DE에서는 Data Discovery라는 용어를 많이 써서 Discoverable을 썼다.
- `Standardized`: **데이터 명명 규칙은 일관적이며 예측가능**해야한다. Airbridge에서는 App, Device, User, EventData 같이 최상위 그룹이 있고 하위 중첩을 통해 데이터를 적재했었다. 이처럼 어떤 정보인지 직관적으로 알기 쉽거나 유추가 가능해야한다.
- has `Semantic Layer`: 특정 비즈니스 지표는 전사가 **일관된 기준과 공식으로만 계산**되어야한다.
    - 기준 일관성: 예시로 iOS 월간 활성 유저(MAU)를 계산하는 기준이 UserID(로그인 유저)인지, IDFA(광고 식별자)인지, IDFV(앱 벤더 식별자)인지 일관되어야한다.
    - 공식 일관성: 예시로 구매전환율 = (취소/환불이 아닌 최종 구매 완료 금액) / (유니크 방문자) * 100(%)여야하며, 순거래액 등을 계산할 때는 쿠폰할인금액을 제해야한다.

### 3. AI Ready

데이터를 믿을 수 있고 분석가들이 원하는 데이터를 찾을 수 있다면, 이 정형화된 과정을 더 가속화 하기 위해 AI를 써야한다는 주장을 했었다. **AI의 먹이는 컨텍스트**이다. AI가 풀고자 하는 문제에 관련된 모든 정보를 연결해야 더 높은 품질을 답변을 받을 수 있다. 문제와 관련된 암묵적 컨텍스트를 문서화하고, 문서들을 최신화하는게 중요하다고 발표했었다. 실제로 에이전트를 만들면서 20개가 넘는 문서들을 최신화했었다. 같은 맥락으로, 에이전트의 똑똑한 답변을 위해서는 이런 것들이 필요하다고 생각한다.

- `Context Ready`
  - 맥락 준비: 사용자의 질문을 올바르게 해석하기 위해 **문제에 대한 맥락이 믿을 수 있으며 쉽게 찾을 수 있어야**한다. Knowledge Base/Graph와 Ontology같은 개념을 말한다. 에이전트가 올바른 답변을 하기 위해서는 사내 맥락들을 연결하고 암묵지의 정보들을 명문화하며 잘못된 답변을 내지 않기 위해 오래된 문서들을 최신화해야한다. 
  - 맥락 유지: 에이전트는 Context Window(기억공간)의 한계가 있으므로 이를 극복하는 수단, 즉 Subagent나 Context window의 외부화, 프롬프트 캐싱 등을 통해 컨텍스트 유지력을 높이는 것을 말한다. [Context Window 한계를 넘어서 – Deep Insight 개발 여정으로 배우는 Context Engineering 실전 기법](https://aws.amazon.com/ko/blogs/tech/context-engineering-from-deep-insight/)를 참고하면 LLM 및 LLM 서비스 내부 구조를 머릿속으로 그려보는데 도움이 됐다.
- `Harness`: 에이전트가 해야하는 행동과 하면 안되는 행동을 명시해야한다. 어떤 문제를 해결하기 위한 유스케이스와 워크플로우를 명시하되, 실행 중 불필요한 혹은 과도한 행동을 하지 않도록 지침과 Hook 등의 도구로 관리되어야한다.
  - 위 글의 다음 시리즈인 [하네스 엔지니어링으로 본 Deep Insight – 로컬 개발에서 프로덕션 운영까지의 설계 여정](https://aws.amazon.com/ko/blogs/tech/harness-engineering-from-deep-insight/)이 도움이 됐다.

Harness의 경우, 요즘 AI 모델들이 똑똑해져서 알아서 문제를 해결할 수 있을 것이라는 막연한 믿음이 있으나 아직까진 명시적인 워크플로우를 정하는게 더 좋다고 생각한다.

그리고 그 당시에 발표하진 않았지만, 요즘 드는 생각들도 있다.

- `Self improving`: 에이전트를 자가발전시켜 목표 달성을 위한 사람의 개입을 줄이는 것이다. 이를 위해서는 피드백 루프가 만들어져있어야 한다. instruction을 자가 수정하는 방법 등이 있다.
- `Traceable`: 에이전트 내에서 어떤 일이 발생하고 있는지 추적 가능해야한다. 에이전트 내에서 어떤 도구를 호출했고, 호출이 실패했는지, 어떤 추론을 실행했는지 추적 가능해야한다.
- `Sustainable`: 1단계와 동일하다. LLM은 비싸다. 동일한 방법으로 비용 관리가 필요하다.

## Future?

이걸 다 했다고 치자. 데이터 플랫폼은 데이터 사용자를 위한 공간이며, 사용자의 최종 목표는 통찰을 얻는 것이다. 그 통찰을 믿을 수 있고, 더 쉽게 접근하고, 기술을 몰라도 자연어로 얻을 수 있게 만들었다.

그렇다면 그 너머는 무엇인가?

- 새로운 데이터가 필요하다면 -> **데이터 파이프라인을 셀프 서비스 할 수 있다.**
- 기존 데이터로 충분하다면
    - 내가 증명하고 싶은 가설이 있다 -> **에이전트를 쉽게 만들 수 있다.**
    - 내가 증명하고 싶은 가설이 없다 -> 사용자가 생각하지 못했던 통찰을 만들어낸다.

가장 마지막은 AGI의 영역인 것 같다. AGI는 연구자들에게 맡기고, 나머지 전자를 더 잘 하려면 무엇을 해야할까?

### 4. Produce Ready

Produce는 **파이프라인이나 에이전트를 생산**한다는 의미로 붙였다. 즉, 내가 증명하거나 해결하고 싶은 문제가 있고 이를 에이전트를 통해 해결하고 싶을 때 쉽게 생산해서 테스트해볼 수 있다는 의미이다.

그렇다면 Produce Ready를 위해서는 어떤 것이 필요할까? 앞서 Physical-Logical-Business-Semantic-Insight라는, 기술로부터 통찰을 얻는 순서를 설명했다. Semantic까지의 준비가 완료됐다면 사용자의 개념과 Semantic을 맵핑하고, 필요한 도구들을 연결하며, 워크플로우를 구성하는 것이 필요해보인다. Data부터 필요하다면 Data를 쉽게 추가하는 것이 필요하다.

그러기 위해서는 Plug-and-Play를 활용할 수 있으면 어떨까. AWS Glue Studio처럼 ETL 파이프라인을 연결해서 구축하고 Agent 또한 비슷한 DX를 가져가면 쉽지 않을까? 즉, 에이전트 셀프 서비스를 할 수 있는 플랫폼을 만드는 것이다. [당근의 멀티에이전트 플랫폼 개발기](https://www.youtube.com/watch?v=mz62uqAXhxo)에서는 에이전트 개발을 플랫폼화하여 사용자가 셀프서비스 할 수 있고, 멱등 및 회귀적 동작을 검증하기 위해 에이전트의 결과에 대한 E2E테스트(올바른 답을 내는가?)와 내부 실행 계획 테스트(올바른 도구를 순서를 지켜 호출하는가? 등)도 포함하여 에이전틱 데이터 플랫폼 개발을 참고하기 좋았다.

## Future of Data Engineering?

2030년을 예상해봤을 때 Data Engineering은 건재할 것 같다. AI도 결국 데이터를 기반으로 움직이다보니, 데이터가 있어야 사용자가 올바른 답을 낼 수 있기 때문이다. 다만, 전통적인 Data Engineering보다는 AI에 의한 데이터 인프라 설계에 더 무게를 둘 것 같다. Semantic Layer, Context Engineering, Harness Engineering, Knowledge Base(or Ontology) 또는 위에서 언급한 사용자가 원하는 에이전트를 쉽게 만들 수 있도록 만드는 플랫폼을 더 만들지 않을까 싶다. 그 때는 또 그 때의 새로운 요구사항이 생기지 않겠는가.
